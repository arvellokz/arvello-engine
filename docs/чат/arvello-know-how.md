# Arvello — приёмы и уроки (что работает, что нет)

Накоплено в чатах первого аккаунта 11–13.11.2026. Читать вместе с `docs/чат/arvello-engine-handoff.md`. Пошаговые навыки — `docs/чат/навыки/` (проверка комплекта, данные Blum).

## Как работать с владельцем
- Коротко, по-русски, без жаргона. Сначала ответ, потом детали. Таблица — когда сравнение.
- Он ждёт, что Claude **делает сам**, а не просит его («ты же сам можешь»). Просить только то, что требует его рук: пароли, вход, скачивание в его браузере, отправка цеху, деньги, удаление файлов в Obsidian.
- Вопросы цеху — только самые нужные (он сам их сокращал с 13 до 4). Всё, что можно решить по нормам, решаем сами с пометкой [М].
- Он мыслит бизнесом: независимость от одного цеха, масштаб на 100+ моделей, экономия лимита. Предлагать дешёвый путь.
- Ночью и при спешке: не останавливать работу на вопросах, решать по умолчанию и записывать решение в журнал.
- Каждое его решение — сразу запись в `docs/ЖУРНАЛ.md` (новые сверху), чтобы сессия кода знала.
- Тексты для Claude Code давать готовым блоком-цитатой «скопировать и отправить». Короткие. Если чат и ChatGPT нашли замечания к одному выпуску — один общий текст, заменяющий прежний.
- Владелец пересылает отчёты сессии кода и ChatGPT как есть (иногда с мусором интерфейса) — не переспрашивать, сразу проверять.

## Цикл работы (как сложилось 13.11)
1. Сессия кода делает и пишет отчёт → владелец пересылает в чат.
2. Чат: `git pull`, сам собирает выпуск, сверяет каждое заявленное исправление по тексту PDF (pypdf) и выборочно глазами.
3. Замечания → `docs/reviews/…` + журнал + push → короткий текст для сессии кода.
4. Второй проверяющий (ChatGPT) → чат **проверяет каждое его замечание** по коду/файлам, отмечает «подтверждено / частично / не подтверждено» и почему, добавляет своё → общий текст сессии кода.
5. Принятый выпуск → копия в Obsidian, старые копии помечаются `УСТАРЕЛО.md`.

## Проверка чужих замечаний (уроки 13.11)
- Не принимать на веру и не отбрасывать: искать в коде (`grep` по `[:90]` и т. п.), в тексте PDF, в логах проверяющего.
- Если у проверяющего ошибка не воспроизводится — искать разницу окружения. Пример: у ChatGPT на Windows строка вылезала за рамку, у нас нет — не было шрифта DejaVu, подставился другой. Лог лежал в Obsidian рядом с его разбором — смотреть такие логи.
- Если проверяющий ссылается на «старую инструкцию» — проверить, какую копию он смотрел (Obsidian мог отставать от GitHub). Отсюда правило: один выпуск, один снимок модели, старые копии помечать.
- Тесты, которые печатают «ИТОГ», но не возвращают код 1, — ложная уверенность. Проверять код возврата (`echo $?`), сейчас это через `testutil.py`.

## Проверка листов (как находить ошибки)
- Генерировать самому (`eng002_kit.py` или `kit13.py`, `export_parts.py`), не верить чужим PDF.
- Рендер `pdftoppm -r 45–60`, склейка по 4 страницы (PIL, 2×2 для A3), смотреть все. Для деталей — один лист крупнее (-r 110 + crop).
- Порядок шагов, названия позиций, таблицы отверстий, В-вопросы — через `pypdf` extract_text, не глазами. Повторы названий: собрать «Поз. N <имя>» со всех листов и посчитать.
- Пересчитывать числа самому: заготовка = готовый − кромка + припуск 1 на сторону с кромкой; привязки отверстий между соседними деталями (дно ↔ стенка ↔ боковина); точки Blum.
- Ориентация вида изнутри: у левой боковины, вид на внутреннюю пласть, перед слева — проверено правилом правой руки.
- Что ловилось: рисунок противоречит тексту; шаг без рисунка; опасный порядок (стена после ящиков — в комоде, потом в шкафу); одинаковые названия у разных позиций (шкаф); текст обрезан без «…»; «без припуска» в вопросе при заготовке с припуском; зенковка в A4 есть, на листе цеха нет; колонтитул чужого изделия; деталь накрывает крепёж; «не согласовано» там, где владелец уже решил.
- Замечание → файл в `docs/reviews/` + короткий текст для сессии кода. Каждое подтверждённое замечание сессия кода превращает в проверку + негативный тест.

## Blum: как добывать точные данные
- **Конфигуратор изделий** (e-services.blum.com/opc), не конфигуратор корпусов (тот не принимает перетаскивание).
  - Поля формы: JS, нативный сеттер `value` + события input / change / focusout; после каждого поля искать элементы заново.
  - Переключатели SAP UI5 (role=switch) — только реальным кликом по координатам; 1 CSS-пиксель ≈ 1,25 пикселя скриншота. Узкая панель: resize_window 1500×950, потом preset desktop.
  - После «Назад» и перезагрузки бывает «An unexpected error» / вечная загрузка — не тратить время, брать данные другим путём.
- **Скачивание во встроенном браузере заблокировано** (ERR_BLOCKED_BY_CLIENT). Обход без скачивания:
  - в сетевых запросах вкладки конфигуратора найти `PAI036/api/functionalunits/<id>/loadPlanningResult` (read_network_requests с requestId) — там раскрой ящика, артикулы и **ссылки на DXF / SVG** всех рисунков;
  - открыть вкладку на `d2.blum.com` и делать `fetch` DXF там же (тот же источник); разобрать секцию ENTITIES: центры CIRCLE = отверстия, подписи размеров — текст в блоках `*D…` (code 1) секции BLOCKS. Наружу выводить только числа, не весь файл. Проверять масштаб 1:1 по известному размеру (453, 440).
  - SVG рисунков: `DOMParser` → тексты `<text>`; сами рисунки смотреть, открыв SVG/GIF во вкладке и сделав скриншот.
  - Из песочницы (curl) d2.blum.com и ikea.com закрыты — только через браузер или файл от владельца в «Загрузки».
- **Каталог Blum 2024** (publications.blum.com/2024/catalogue/en/): текстовый слой страницы — `files/assets/common/page-vectorlayers/NNNN.svg`, где **NNNN = печатная страница + 4**. Поиск по разделам: пройти страницы fetch-ем и искать артикул в тексте.
  - Значки таблиц (◐, ○) есть только на растре `page-html5-substrates/pageNNNN_3.webp`: открыть SVG-страницу, вставить `<image>` растра под текст, увеличить ширину SVG до 3000–9000 px, прокрутить и сделать скриншот.
  - Легенда крепления направляющих: **A** (саморезы) — все места ○ и ◐; **B** (системные винты Ø6) — только ◐; * — можно заменить саморезом.
  - Важные страницы: MOVENTO крепление с. 428; TANDEM 560H с. 460, с TIP-ON с. 528; петли CLIP top с. 76–77; планки с. 150–156; TIP-ON дверей с. 192–193; крепёж с. 160.
- **Ловушки, на которых уже ошибались:** 173H7100 — планка под саморезы (с евровинтами — 173L8100); размеры 45 / 9,5 у петли — от варианта INSERTA, у screw-on Blum их не даёт; точка 28 есть только у 766H; +1 мм к оси 38 нужен Blum только при установке профиля до сборки корпуса; NL зависит от глубины корпуса (комод со столиком 530 → NL 480, без — 500 → NL 450).

## GitHub и файлы
- Перед записью `git pull -q --rebase origin main`; писать в журнал вставкой после строки «## Записи (новые сверху)» (sed `0,/…/s//…/`).
- Если push не проходит — вызвать add_repo (access push) для arvellokz/arvello-engine, затем `git -c push.negotiate=true push`.
- Сессия кода может работать в своей ветке `claude/…`; забирать `git fetch origin refs/heads/<ветка>:refs/remotes/origin/<ветка>`, проверять `merge-tree`. Вливать в main — только с «да» владельца.
- Obsidian ↔ песочница: `device_request_folder_access` (узкая папка, один раз) → `device_list_dir` → `device_stage_files` (появляется в /mnt/user-data/uploads/…, подождать 1–2 с) → обработка → копия в /mnt/user-data/outputs/ → `device_commit_files` (force для своих файлов). Удалять на компьютере нельзя без device_bash — помечать `УСТАРЕЛО.md`.
- Владелец не видит файлы песочницы: важные PDF — SendUserFile + копия в Obsidian.
- Входные файлы для сессии кода класть в `docs/inputs/<дата>_<задача>/` с README (откуда, что не скопировано).
- Email владельца в файлы репозитория не писать.

## Экономия лимита
- Длинный чат дорог: каждое сообщение пересчитывает всю историю. Начинать новый чат по `arvello-engine-handoff.md`, а не тянуть старый.
- Крупные PDF читать разделами; таблицы и подсказки — текстом, картинки — только где нужен вид (склейки по 4 при 45–60 dpi).
- Не перечитывать то, что сессия кода уже проверила; проверять выборочно главное (заявленные исправления + 2–4 листа глазами).
